# 发布链路（2026-09-28 跑通）

桌面端「打 tag → CI 打包 → GitHub Releases」发布流水线的标准操作、配置承重点与踩坑实录。首版 v0.1.0 已全绿跑通（Release run 约 13 分钟出双架构产物）。上游衔接：《产品与项目管理评审-2026-09-24.md》附录 A（建仓 runbook，已完成）。

## 一、发版标准流程（SOP）

```bash
# 1. 版本号对齐：package.json 的 version 必须与 tag 一致（产物名、release 名都取自它）
#    例：0.2.0
$ git commit -m "chore(release): v0.2.0" && git push origin main

# 2. 打 tag 并推送（annotated tag）——push 即触发 release workflow
$ git tag -a v0.2.0 -m "知叶 0.2.0"
$ git -c http.proxy=http://127.0.0.1:7890 push origin v0.2.0

# 3. 等 Actions 跑完（约 13 分钟，两个 macOS job 并行）
#    监控：https://github.com/zhangzhengyang27/zhiye/actions

# 4. 发布草稿：Releases 页 → v0.2.0 draft → 清点资产 → Publish
#    https://github.com/zhangzhengyang27/zhiye/releases
```

要点：

- **产物挂 draft（草稿）**，不自动对外发布——最后一页必须人工点 Publish，这是有意的闸口。
- **失败轮会留残留**：electron-builder 每个 job 各建一条 draft；若某轮失败过，发布前检查是否有多余 draft / 错名资产，删掉再发布（API 清理见第四节）。
- **改了 workflow 或构建配置后，必须挪 tag**（删远端 tag 重打重推），Re-run 旧 run 只会用旧 commit SHA，白烧 macOS runner 分钟数：
  ```bash
  git push origin :refs/tags/v0.2.0   # 删远端 tag
  git tag -d v0.2.0 && git tag -a v0.2.0 -m ... && git push origin v0.2.0
  ```
  失败 run 没有产出资产时挪 tag 无副作用；若已产出半套资产，发布前清理。

## 二、流水线构成与承重配置

| 文件 | 职责 | 承重点 |
| --- | --- | --- |
| `.github/workflows/release.yml` | `v*` tag 触发 | matrix 双 runner：`macos-latest`(arm64) + `macos-15-intel`(x64)；`--publish always` 上传；`CSC_IDENTITY_AUTO_DISCOVERY=false` 跳签名 |
| `.github/workflows/ci.yml` | main push/PR 验证 | typecheck / lint / vitest / build:web（`ELECTRON_SKIP_BINARY_DOWNLOAD=1` 不装 Electron 二进制） |
| `electron-builder.yml` | 打包配置 | `artifactName: zhiye-${version}-${arch}.${ext}` **承重勿删**（见坑 2）；publish 段指向 github zhangzhengyang27/zhiye |
| `package.json` | `build:mac` 脚本 | `pnpm build && electron-builder --mac`；version 字段是产物名与 release 名的事实源 |

产物清单（每次发版 9 件）：`zhiye-{版本}-{arch}.dmg / .zip` + 各自 `.blockmap`（增量更新用）+ `latest-mac.yml`（electron-updater 元数据），arch = arm64 / x64。

**加回 Windows**（仅 macOS 是 2026-09-24 的决策，若推翻）：release.yml matrix 加一行 `windows-latest + build:win`，package.json 加 `build:win` 脚本，electron-builder.yml 补 win 段（参照 MelodyAir 仓 `.github/workflows/release.yml`）。

## 三、踩坑实录（已修，但条件复现）

### 坑 1：GitHub Packages 403（安装内核包失败）

- **现象**：CI `pnpm install` 死在 `ERR_PNPM_FETCH_403` 拉 `@zhangzhengyang27/yuque-editor-core` tarball；本机能装（本机 `~/.npmrc` 有 PAT）。
- **根因**：GitHub Packages 规则——**用户名下的包默认只授权给「发布它的那个仓库」**。zhiye 仓的 `GITHUB_TOKEN` 认证能过（401→403 说明 token 有效）但无权读包。仓库 `.npmrc` 按约定不含 token（只有 scope registry 映射），认证必须在 CI 侧注入。
- **解法（两半，都已做）**：
  1. workflow 侧：permissions 加 `packages: read`，install 前把内置 token 写进 runner 用户级 `~/.npmrc`：
     ```yaml
     - name: Setup GitHub Packages auth
       env:
         NODE_AUTH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
       run: echo "//npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}" >> ~/.npmrc
     ```
  2. 网页侧（**无 API 可代做**，2026-09-28 用户已授权）：https://github.com/users/zhangzhengyang27/packages/npm/yuque-editor-core/settings → Manage Actions access → Add repository `zhiye`（Read）。
- **何时复发**：换包名 / 换发布仓时需重新网页授权；新 workflow 文件若漏写 npmrc 认证步骤则 401/403。

### 坑 2：中文产物名上传崩溃（本地测不出）

- **现象**：构建成功、上传 GitHub Releases 时报 `TypeError: Request path contains unescaped characters`，job 中断。
- **根因**：productName 是中文（知叶），默认产物名带中文，electron-publish 的 Node http 客户端拒绝未转义路径。**本地打包不上传，永远测不出来**。
- **解法**：`electron-builder.yml` 固定 ASCII 产物名（已加，承重勿删）：
  ```yaml
  artifactName: zhiye-${version}-${arch}.${ext}
  ```

### 坑 3：安装报「“知叶”已损坏，无法打开」（签名断裂，2026-09-28 已修）

- **现象**：从 Releases 下载 dmg 安装后打开，macOS 弹「“知叶”已损坏，无法打开。你应该将它移到废纸篓」。
- **根因（codesign 实测定位）**：不是产物真损坏——electron-builder 在无证书时**完全跳过签名**，但 Electron 二进制自带 linker-signed ad-hoc 签名；打包改动 bundle（改名、Info.plist、图标）后残留签名**校验断裂**（`codesign --verify --deep --strict` 报 `code has no resources but signature indicates they must be present`）。Gatekeeper 对带 quarantine 属性且签名无效的 app 直接报「已损坏」。**「右键 → 打开」对这条报错无效**。
- **修复（已进 release.yml，commit 64fa14f）**：build 命令加 `-c.mac.identity=-` 显式 ad-hoc 重签——打包后整个 bundle 重签，`codesign --verify` 通过（flags `adhoc,runtime`），启动实测无崩溃。代价是报错从「已损坏」降为「无法验证开发者」，且真证书接入后此参数要让位给正常证书发现（删掉或调整即可）。
- **用户侧解法（发给测试者的标准话术，两种报错都适用）**：把「知叶」拖入应用程序文件夹后，终端执行：
  ```bash
  xattr -cr /Applications/知叶.app
  ```
  然后正常打开即可。（也可在 dmg 挂载后对卷内 app 执行再安装。）
- **治本**：Developer ID 签名 + 公证（需 Apple Developer Program），见第五节未完成事项第 1 条；在解决前，**每次发版 Release notes 必须带上面的安装说明**。

### 坑 4：runner 分钟数（私仓相关）

仓库若转 private：GitHub macOS runner 按 **10 倍**计费，免费额度折算约每月 200 分钟真实 macOS 时间，一次双架构 release 就可能吃掉大半。当前 public 仓 Actions 免费。转私前先评估，或 matrix 只留 arm64。

## 四、CI/Release API 操作工具箱（执行环境无 gh CLI）

- **代理**：所有 GitHub API 调用走 `curl --proxy http://127.0.0.1:7890`（zsh 变量不分词，代理 flag 要显式写全，不能塞变量）。
- **认证 token**：用 `git credential fill` 从凭据库取本机缓存的 PAT（scope 有 repo + workflow，**无 read:packages 但够用**——rerun / cancel / 删资产 / 读日志都行）；token 不回显、不入库：
  ```bash
  token=$(printf "protocol=https\nhost=github.com\n" | git credential fill | sed -n 's/^password=//p')
  ```
- **常用端点**（均带 `-H "Authorization: Bearer $token"`）：
  - 列 run：`GET /repos/zhangzhengyang27/zhiye/actions/runs?per_page=N`
  - job 明细（失败步骤定位）：`GET .../actions/runs/{run_id}/jobs`
  - 日志（可 grep 401/403/⨯）：`GET .../actions/jobs/{job_id}/logs`
  - 重跑失败 job：`POST .../actions/runs/{run_id}/rerun-failed-jobs`（201=受理）
  - 取消 run：`POST .../actions/runs/{run_id}/cancel`（202=受理）
  - 删残留 draft / 资产：`DELETE /repos/.../releases/{id}`、`DELETE /repos/.../releases/assets/{id}`（204）
- git push / ls-remote 同样要 `-c http.proxy=http://127.0.0.1:7890`（工作区 AGENTS.md 坑 1）。
