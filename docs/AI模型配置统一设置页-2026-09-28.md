# AI 模型配置统一收进设置页（2026-09-28）

## 背景与决策

原大模型配置（API Key / Base URL / 模型 / 超时，DeepSeek + OpenAI 兼容双提供方、多 profile）
挂在**画板编辑器**的「模型配置」弹层里（el-dialog + 草稿/保存流程），文档 AI 面板与 AI
写作页只读同一份本地配置却没有编辑入口。本批把它统一收进**偏好设置页**（`/settings`）：

- 设置页在「加入内测版体验计划」与「关于」之间新增**「AI 模型」分组**（自有差异组，
  语雀无此分组，不破坏前 9 组的语雀像素基线——新增组随滚动出现在末尾前一档）；
- 画板编辑器删除配置弹层，头部按钮改为**「模型设置」**（只读当前模型摘要 + 跳转设置页）；
- 未配置密钥时的校验文案指向「偏好设置 → AI 模型」。

存储模型不变：仍按账号存本机（`kb-board-ai-config:{userId}`），桌面端系统密钥链 /
Web 端 AES-GCM，密钥不进数据库、不落服务端；后端 `AI_API_KEY` env 兜底链路不变。

### 1. 模型下拉框展开异常（校准层 filterable 首命中）

  上，与根 `:focus-within` 描边叠成「空绿框」双线。

修复（element-plus-calibration.css el-select 段追加两条）：filterable 实例（wrapper 带
`is-filterable`，特异性 (0,6,0) 压过自家 revert）恢复 EP 的 absolute + top 50% +
translateY 叠放；`.el-select__input:focus-visible` outline:none（焦点环语义由根承担）。

## 追加批 2（2026-09-28 晚）：Web 端设置页「无法返回」体感修复

用户反馈网页端设置页无法返回。实测主窗口直达时「＜」按钮路由跳转正常，真正的问题是
**返回语义与窗口形态不匹配**：Web 端偏好设置入口走 `openSettingsWindow()` 弹独立小窗
（830×768），窗内点「＜」执行 `router.push(knowledge)` 会让小窗原地变成完整知识库
列表页——观感即「无法返回」，且主窗口不受影响，用户语义上的「回到主界面」根本没发生。

修复（DesktopSettingsView.vue）：返回按窗口形态分流——

- 独立设置窗（`window.xiaoyeDesktop` 存在，或 `window.opener` 未关闭）：`window.close()`
  关窗，焦点自然回主窗口；按钮 title 相应为「关闭设置窗口」；
- 主窗口直达（直接输 URL / 刷新，无 opener）：维持 `router.push(knowledge)`，title「返回」。

三场景实测：弹窗点返回 → 窗口关闭 ✓；主窗直达点返回 → 跳 /knowledge ✓；重复开合同样
正常 ✓。桌面端独立设置窗同享关窗语义（Electron 渲染层 window.close() 由主进程关窗）。

## 追加批 3（2026-09-28 深夜）：Web 端设置改为标准页面导航

用户追问「web 端为什么不能设计个返回的按钮」——关窗语义仍不符合 Web 习惯，根源是
Web 端照搬了语雀桌面端「设置 = 独立窗」的形态。本批把 Web 端改回标准页面导航：

- **入口**：`openSettingsWindow()` 收窄为桌面专用（desktop-bridge.ts 删除 window.open
  分支与 SETTINGS_WINDOW_FEATURES）；侧栏「更多 → 偏好设置」与 App.vue 的 ⌘, 兜底在
  Web 端改为 `router.push({ name: "settings" })`——主窗口内直接打开，不再弹窗/弹标签；
- **返回**：设置页「＜」按端分流——桌面独立窗 `window.close()`；Web 端应用内导航而来
  （vue-router 写入的 `history.state.back` 有值）则 `router.back()` 原路返回（文档页/
  工作台/列表页都能回），新标签直输 URL 兜底 `push(knowledge)`。**不判 history.length**：
  新标签的 about:blank 初始项会让 back() 退出应用（实测踩中后改 state 判定）；
- **verify:settings**：入口两条断言从「监听弹窗」改回主窗口路由断言，并新增「设置页
  「＜」原路返回」检查（32 项全绿）。

实测：菜单/⌘, 进设置均为主窗口路由（确认未弹窗）；从工作台进设置返回原路回工作台；
全新标签直输 /settings 返回兜底回 /knowledge。桌面端独立设置窗行为不变。

## 追加批 4（2026-09-28 深夜）：Web 端兼容性横扫

顺着形态决策横扫全仓「桌面专属能力在 Web 的降级」与「窗口形态假设」，修两处：

1. **AccountView.goBack 同款历史判定漏洞**：`history.length > 1` 在新标签直输
   /account 时也为真（about:blank 初始项），back() 退到空白页退出应用——与设置页
   同步改用 `history.state.back`（vue-router 写入，应用内导航才有值）判定。
   实测：新标签直输 /account → 返回 → /knowledge ✓。
2. **KB「更多设置」Web 端弹标签**（KnowledgeWorkspaceHomeView.openSettings）：
   桌面端开独立窗（对齐语雀），Web 端 window.open 弹 `/kb-settings/:kbId`——该独立
   视图无返回钮，用户只能关标签。改为 Web 端主窗口路由进工作台内嵌设置页
   （knowledge-settings），与偏好设置同构；桌面端不变。

排查确认无需改动的面：openSettingsWindow 收窄后无残留调用；10 处 window.open 均为
合理的新标签场景（分享链接/文档 URL/打印窗）或已有桌面分流；bootstrapLoginWindow、
onDeepLink、openDocumentInNewWindow 各调用点均有 `window.xiaoyeDesktop` 判定；KB
内嵌设置的其它四个入口（搜索页/命令面板×2/概览/工作台布局）本就是主窗口路由；
verify-desktop-native 断言的是桌面独立窗行为（未变）。

已知可接受项：设置页 780px 固定内容列在窄于 ~844px 的浏览器窗口下出现横向滚动
（复刻语雀桌面基线，移动端不在本期范围）。
